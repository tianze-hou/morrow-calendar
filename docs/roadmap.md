## P0 · 建议下一轮做

### 1. 重复日程（RRULE 展开 + 三种编辑范围）

接口和字段都已经就位：`rrule` / `exdates` 早在契约里预留且恒为空，现在也一直照原样返回。要做的是挂上 `recurrencePlugin`，后端实现 RFC 5545 展开与 EXDATE，并在编辑 / 删除时提供「仅此次 / 此日程及后续 / 全部日程」三种作用范围。大约 2–3 个半天。

这是全项目最复杂的一块。冲突检测要从「两条区间重叠」升级为「展开后的实例两两比对」；跨时区碰上夏令时容易出错；三种编辑范围会在库里产生「主事件 + 例外实例」的结构，DELETE / PATCH 的语义得重新定义。建议单独开一轮，先只做「每天 / 每周 / 每月 + 永不结束」。

用户已明确本轮不做，推迟到下一轮。

## P1 · 体验与数据完整性

### 5. 日程提醒与通知

提前 N 分钟提醒，服务端轮询，推送走浏览器通知，视需要再扩展到邮件 / Webhook。约 2 个半天。需要一个常驻进程，systemd / pm2 已经能守。难点还是时区和夏令时；另外提醒规则要表达重复日程，所以得排在 #1 之后。

### 6. iCalendar 导入（.ics）

导出那半边已经完成（`GET /api/export/events.ics`，见「已完成」）。剩下的是读别人的文件：解析 VEVENT、把外部字段映射到 `title / start / end / allDay / location / description`，并且在落库前先判断是不是重复——同标题同时间的两条，八成是同一条日程被导了两遍。约 1–1.5 个半天，建议走 `dry_run` 先给预览，让人看过再写。

几个具体的坑：别的日历会把时区写在 `VTIMEZONE` 里而不是 `TZID` 里，只认 `TZID` 会静默按服务器时区解释；`DTEND` 对 `VALUE=DATE` 是开区间，导进来要减一天，否则全天日程会多占一天（这是导入侧最容易漏的一条，我们的导出已经在做镜像处理）；重复的 `RRULE` 目前落到 `rrule` 字段也只能如实存下、不展开。

### 8. 搜索增强与统计视图

跨全部历史的关键词搜索、按分组 / 地点的聚合统计、空闲时段查找。约 1.5 个半天，风险低。数据量大了要给 `title` 加索引，或者上全文索引。

### 13. 界面多语言（i18n）

目前文案分两处：自己写的界面文字散在各组件里，`@ilamy/calendar` 的 92 项内置翻译集中在 `src/i18n/zh-CN.ts`。要做的是抽出 zh-CN / en-US 两套资源，语言偏好按用户持久化（复用 `settings` 表，和 `theme` 一样的存法），首屏从本地缓存读取以免闪一下默认语言。约 2 个半天。

这块不用动接口，也不用动数据模型：错误响应里的 `code` 早就是稳定枚举，前端按 code 自己映射文案即可，后端返回的 `message` 继续当兜底展示。相对麻烦的是英文排版会比中文短一截，按钮与标签的宽度要重新过一遍；以及日历里的星期与月份缩写得跟随 `dayjs` 的 locale 切换，别只换了一半。

### 14. 键盘快捷键

**本轮已做**（见「已完成」）：高频动作、速查表、输入框放行都到位了。当时列的三个坑的落法是：`Ctrl+S` 在 `EventDialog` 里 `preventDefault` 掉；焦点在输入框时字母键整体放行，`Ctrl/⌘+Z` 也只从提示条的「撤销」走软删除恢复；速查表由绑定数组生成，不另写文案。

**还没做的**：

- **通用的撤销 / 重做栈**。现在只覆盖「删除」（且只限软删除——回收站里彻底删掉之后就没了）。要真正做 `Ctrl+Z` / `Ctrl+Shift+Z`，得在客户端记一串可逆操作（新建 → 删除、修改 → 改回、拖拽 → 挪回），并且和 `version` 乐观锁对齐：别人改过之后，撤销要变成「基于过期版本的覆盖」还是干脆拒绝，得先定。约 1 个半天。
- **上一 / 下一周期（`←` / `→`）**。故意没绑：日历内部的网格与拖拽已经吃掉方向键，硬插一手会和它打架。要做得先确认组件在什么焦点状态下不处理方向键。
- **搜索（`/` 或 `Ctrl+K`）**。界面还没有搜索框，等 #8 落地再顺手接。

### 16. MCP 的 OAuth 2.1（为了覆盖 ChatGPT）

**一句话**：让 ChatGPT 也能连，并让外部用户免去「手工生成令牌再粘贴」这一步。

阶段一交付的 MCP 用 Bearer 令牌鉴权，Claude Desktop / Cursor / Claude Code 已经能直接用，
但 ChatGPT 有两条更严的要求：**只认公网 HTTPS 的 MCP 服务器**，且**走标准的 OAuth 授权流程**。
此外多个来源称 ChatGPT 个人版（Plus / Pro）的自定义连接器只给读权限，写工具不会触发，
写能力需要 Business / Enterprise / Edu —— 这一点在做之前值得先确认目标用户的套餐。

要做的事：加一个授权服务器（PKCE、动态客户端注册、令牌签发与刷新），
并把现有的 `users` / `api_tokens` 体系接到 OAuth 的 subject 上。
约 3–4 个半天，风险中：OAuth 本身的细节不算多，难在各家客户端的行为差异，需要在真实客户端反复联调。

如果暂时只要服务自己人与 Claude / Cursor，这一项可以一直往后放。

## P2 · 更远一些

### 9. 参与人与会议室（资源视图）

启用 `resources`，按人或会议室排布时间轴，冲突检测升级到资源级。3 个半天以上。多用户已经就绪，可以直接排。麻烦在于资源级冲突会和人「有没有空」的规则耦合在一起，业务复杂度明显上升。

### 10. 移动端适配与手势

窄屏下以日视图和日程列表为主，加触摸拖拽。约 2 个半天，风险低，但要在真机上实测。

### 11. CalDAV 同步

对外提供 CalDAV 端点，让系统日历或手机自带日历能双向同步。4 个半天以上，风险高：协议本身复杂，而且 RRULE 不支持的话同步会丢重复事件，所以建议排在 #1 之后。

### 12. 日历分组共享

把某个分组共享给另一个用户，可只读也可写。约 2 个半天。麻烦的地方是权限矩阵要重新设计：目前「一条日程只属于一个用户」是硬假设，共享会打破它，所有查询的 `user_id` 过滤都要改成「owner 或已被授权」。本轮明确暂不做，但表结构（`calendars.user_id`）刻意留了扩展余地。

### 15. 服务端 AI 上下文：长期记忆 + 操作流水

**一句话**：把「当前这个实例到底是怎么回事」做成服务端的一等数据，让接入的模型和人读到同一份真相。

问题出在 AI 每次都从零开始。它能看到日程数据本身，却看不到「这个人有什么偏好」「上次是谁把这条挪走的」「这几条为什么被删掉」。这些知识要么散在对话历史里（模型看不见），要么只有人记着（模型读不到）。结果是每次都要重新交代一遍，而人工改过的东西 AI 完全不知道。

构想是拆成两份、共用一套读写口：

1. **长期记忆（人工维护）**——量少、显式写入：时区与作息习惯、命名和分组约定、当前目标、明确的禁忌。像一份随实例走的 `MEMORY.md`，但存在库里、带版本号。
2. **操作流水（自动追加）**——服务端在每次写操作时自己记一笔：谁（用户 / 智能体 / 令牌名）、何时、对哪条数据、做了什么（含关键前后值）。只增不改，可按游标增量拉取。

读口希望做到「一次请求拿全」：调用方拉一次就同时拿到记忆与「上次我来之后发生了什么变化」，直接进上下文窗口。写口只开放记忆那一份，流水由服务端自己产生，不接受客户端伪造。

动手前要先拍板几件事：

- **和 `SKILL.md` 的分工**。`skills/morrow-calendar/SKILL.md` 讲「怎么操作」（静态、随仓库版本走）；这份上下文讲「现在是什么情况」（动态、随实例走）。两者不能互相抄，否则迟早对不上。
- **谁来写记忆**。只让 AI 写会漂，只让人写会荒。倾向「AI 提议、人确认」，但得先定一个不变成负担的最小流程。
- **注入风险**。这份内容会被直接塞进提示词，等于喂给模型非受信输入。任何写入点都要有归属和审计，也不能让外部来源（导入的 `.ics`、分享链接）间接写进来。
- **范围**。每实例一份还是每用户一份？多用户下「记忆」天然私有，流水则要想清楚谁有权读谁的。
- **和 git 的边界**。它是运行时数据，不进仓库，备份跟着 `calendar.db` 一起走。

**估算**：上面几个问题本身就要一轮讨论；之后实现（两张表 + 读 / 写端点 + 在各写操作里插流水）约 2–3 个半天。

## 我的建议

先做 #1（重复日程）。它是唯一会动到数据模型核心的一项，需要单独留一整轮时间和一轮回归测试。之后按 #6（.ics 导入）→ #8（搜索与统计）走，这两项风险低，也能立刻用上。

#14 键盘快捷键主体已经做完，剩通用的撤销 / 重做栈（1 个半天），随时可以插进任意一轮。
#16（OAuth 2.1）取决于要不要服务 ChatGPT 与外部用户——不是要先在前/后 Depends，可以独立排期，但务必在实际客户端上验证过再宣布支持。
#15 不参与排队——它需要先单独聊一轮设计，把上面那几个问题定下来，再决定插在哪。
